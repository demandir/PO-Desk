# PO Desk architecture

PO Desk is a small single-tenant purchasing workflow sized for roughly 100 employees and no more than 30 requests per week.

## Runtime layout

```text
GitHub Pages
  React + Vite static SPA
      |-- anonymous submit/status lookup --> Supabase Edge Functions
      |-- administrator sign-in ----------> Supabase Auth
      `-- scoped admin reads/updates ------> Postgres + row-level security

Supabase
  Postgres: departments, profiles, purchase orders, line items, audit events
  Auth: department administrators and one global administrator
  Edge Functions: anonymous validation, abuse controls, request-code lookup
  Storage: not used in this release; quotes are HTTPS links rather than uploads
```

GitHub Pages serves only public browser code. The Supabase anonymous key is intentionally public and identifies the project; authorization is enforced by Postgres row-level security and server functions. The Supabase service-role key and Turnstile secret exist only as Edge Function secrets.

## Roles and boundaries

- Employees have no account. They submit a complete request and receive one private request code. The sequential PO reference remains an internal administrator identifier.
- Department administrators authenticate and can read or transition only purchase orders assigned to their department.
- The global administrator can read every department, see aggregate statistics, transition any request, and add departments.
- Public status lookup accepts the private request code and returns only status and dates. It does not return names, email addresses, prices, item descriptions, internal PO references, or review notes.
- Status changes create append-only audit events. References, timestamps, totals, and request-code hashes are generated by the database, not trusted from the browser.

## Availability and recovery target

- Target availability: 99.5% per calendar month for the composite employee workflow.
- Planning latency targets: p50 200 ms, p95 500 ms, p99 1,000 ms for backend requests. These are targets, not measured production results.
- Capacity assumption: 10 reads per write, with a 5 requests/second peak budget. The sole developer/owner owns the error budget.
- Recovery point objective: 1 hour.
- Recovery time objective: 4 hours.

Monitor the full service with a five-minute synthetic check that submits a test request, signs in with a monitoring administrator, lists the request, and performs a permitted transition in a dedicated test department. Alert separately on authorization leakage; the acceptable cross-department access rate is zero.

The one-hour recovery point cannot be met by source control alone. Enable Supabase point-in-time recovery or schedule encrypted database exports at least hourly, and test restoration before calling this target operational.

## Data lifecycle

This release stores requester name, department, vendor, items, prices, business reason, optional project/quote references, and review history. Requester email, delivery, shipping, and tax are not collected. Administrator email is managed by Supabase Auth. Payment-card data, bank information, government identifiers, health information, credentials, and secrets do not belong in purchase requests. Define a retention period under company policy before launch.

No email notification system is included. Administrators review the dashboard, and requesters use their single request code.

Pending submissions retain the original payload and random identity in session storage until confirmed. Uncertain responses offer a safe retry with the same identity; PostgreSQL serializes matching attempts and returns the original receipt. A status lookup can recover a successful submission when its response was lost. All totals are calculated from item quantities and unit prices, limited to two decimal places. The dashboard fetches every authorized page instead of silently truncating at 250 records.
